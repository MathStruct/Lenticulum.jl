Graphs

Mycelium.Absorbing — Type
Absorbing()

Variable → factor only. The factor consumes on this channel and never writes it, so the channel is never Unobserved(). A loss and the input side of an ordinary layer are absorbing.

source
Mycelium.AbstractMessageRule — Type
AbstractMessageRule

How a factor node computes its outgoing messages: BeliefPropagation, the default, MeanField, ExpectationPropagationRule or MixtureReduction. Chosen per node with factor!(b, name, f; rule).

source
Mycelium.BeliefPropagation — Type
BeliefPropagation()

Sum-product messages: the factor is inverted against the cavity (variable → factor) messages of its other channels. The default rule of every factor node.

source
Mycelium.Bidirectional — Type
Bidirectional()

Messages flow both ways. The attached channel may be Observed() or Unobserved() depending on the message being computed — this is what makes a factor implicit.

source
Mycelium.Edge — Type
Edge(factor, channel, variable, direction, coupling)

Attaches channel channel of factor node factor to variable node variable.

coupling selects the boundary derivative in graph parameter gradients. detach=true passes values in both directions and suppresses every derivative crossing this edge. The AD rules support ForwardDiff and ChainRules reverse mode. Fixed-reference replay also defines the cuts for central differences. Unknown coupling types throw.

source
Mycelium.EdgeDirection — Type
abstract type EdgeDirection

Which way messages may travel along an edge. The graph is directed; bidirectional edges are the special (and, for implicit factors, usual) case.

source
Mycelium.Emitting — Type
Emitting()

Factor → variable only. The factor produces on this channel and never reads it, so the channel is never Observed(). A data source, a prior, and the output side of an ordinary Lux-style layer can all send emitting messages. For graph free energy, a factor with uses_cavity (including PriorFactor) needs Bidirectional() instead, so it can also receive the cavity message.

source
Mycelium.ExpectationPropagationRule — Type
ExpectationPropagationRule()

Expectation-propagation messages (Minka 2001): the belief-propagation message $m_t$ is computed as usual, and when it leaves the target's family (a mixture of Gaussians, say) the tilted belief $\pi_t\, m_t$, with $\pi_t$ the target's cavity (excluded marginal), is projected onto the family by matching moments (ep_project) and the cavity is divided out (ep_divide):

\[m_t^{\mathrm{EP}} \;=\; \operatorname{proj}\bigl[\pi_t\, m_t\bigr] \,/\, \pi_t .\]

A message already in its family is sent unchanged, so on a Gaussian graph the rule is belief propagation. Gaussian division is subtraction of canonical parameters; the site may have an indefinite precision and is then declared improper. An update whose cavity is not a proper Gaussian, or whose tilted belief has a component that is not, is skipped: the edge keeps its previous message. Lenticulum's ExpectationPropagation is a different thing: the inversion method of a LikelihoodFactor. Iterate to a fixed point (with damping if it oscillates); one tree sweep is not one. The graph free energy counts the node as a belief-propagation node, which at a fixed point is the expectation-consistent Bethe free energy (passing.md, "Expectation propagation").

source
Mycelium.FactorGraph — Type
FactorGraph

A bipartite graph of variables and factors with named, directed channel attachments.

Build one with GraphBuilder; do not construct directly, since the adjacency indices must stay consistent with the edge list.

source
Mycelium.FactorNode — Type
FactorNode(id, name, factor)

A node holding an AbstractLenticulumFactor — a parameterized statistical game — together with its frozen parameter paths, its AbstractMessageRule and its parameter key params: the entry of the graph's parameter and state trees it reads. The key is the node's name unless factor!(...; params) ties it to other nodes (parameter_key).

source
Mycelium.GraphBuilder — Type
GraphBuilder()

Mutable builder. Use variable!, factor!, connect!, then build.

source
Mycelium.MeanField — Type
MeanField()

Mean-field messages: the message to channel $t$ is $\exp \mathbb E_{\prod_{i \ne t} q_i}[\log f]$, taken over the current marginals $q_i$ of the other channels' variables rather than their cavity messages, computed by mean_field_message. Mixing such nodes with BeliefPropagation nodes gives the hybrid of Riegler et al. (2013): exact within the BP part, factorised across the mean-field nodes. Iterate a sequential schedule to a fixed point; one tree sweep is not one. The graph free energy is then the merged free energy of that paper, eq. (17), with each mean-field node's mean_field_energy (free_energy.md).

source
Mycelium.MixtureReduction — Type
MixtureReduction(maxcomponents)

Mixture messages with a budget: the factor → variable message is the exact one, with every mixture input expanded into its components (mixture_message) instead of collapsed to its moments, and then reduced to at most maxcomponents components (reduce_message; for Gaussian mixtures Runnalls' merge). MixtureReduction(1) is assumed-density filtering on the outgoing message; a large enough budget is exact belief propagation with mixtures. The graph free energy is not defined for these nodes, and is refused.

source
Mycelium.VariableNode — Type
VariableNode(id, name, space)

A wire. Carries a belief; has no behaviour of its own.

Per AutoBayes' Remark 24 (and the design note [[Everything is a Factor]]), data is not a variable — data is a DataFactor of arity one attached to a variable. Variables are purely structural.

source
Mycelium.build — Method
build(b::GraphBuilder) -> FactorGraph

Freeze the builder into an immutable graph with adjacency indices.

Frozen factors are accepted. Structural validate checks remain optional; parameter freeze paths are checked against the parameter tree when it is supplied. Tied nodes (one parameter_key) must agree in factor type and freeze, and a key may not be the name of a node that reads another key; otherwise this throws.

source
Mycelium.channels_of — Method
channels_of(g, fid) -> Tuple{Vararg{Symbol}}

The channel names of factor fid that are actually connected in this graph. A factor may declare more channels than the graph uses; the unused ones are Latent() in every message.

source
Mycelium.connect! — Method
connect!(b, factor::Symbol, channel::Symbol, variable::Symbol;
         direction = Bidirectional(), coupling = DiagonalCoupling(), detach = false)

Attach one channel of a factor to a variable.

Each (factor, channel) pair may be connected at most once: a channel is a single port, not a bus. Fanning a variable out to several factors is done by connecting those factors, which is the graph-level form of the copier of Copiers Cups and Caps.md.

All four built-in couplings are accepted. A detached edge overrides its coupling. Non-diagonal parameter gradients require an explicit static replay schedule. Support restrictions are checked when gradients are requested, with explanatory ArgumentErrors.

source
Mycelium.euler_characteristic — Method
euler_characteristic(g) -> Int

$|F| + |V| - |E|$.

Equal to 1 exactly when the graph is a connected tree, and 1 - L when it has L independent loops. It is also the sum of the Bethe counting numbers $\sum_f 1 + \sum_v (1 - d_v)$, since $\sum_v d_v = |E|$ — so this single integer says how badly the free-energy bookkeeping over-counts. See free_energy.md.

source
Mycelium.factor! — Method
factor!(b::GraphBuilder, name::Symbol, factor; freeze = (), rule = BeliefPropagation(),
        params = name) -> Int

Add a factor node wrapping an AbstractLenticulumFactor; returns its id. freeze is :all, a parameter path such as (:encoder,), or a tuple of paths. Paths select complete subtrees and are checked against the actual parameter tree. rule is how the node computes its messages: BeliefPropagation, MeanField, ExpectationPropagationRule or MixtureReduction. params is the node's parameter_key: nodes given the same key share one entry of ps and st (their gradients add), and must have the same factor type and freeze; build checks.

source
Mycelium.isconnected — Method
isconnected(g) -> Bool

Whether the undirected bipartite graph is connected.

source
Mycelium.isdag — Method
isdag(g) -> Bool

Whether the directed multigraph induced by the edge directions has no directed cycle.

An Emitting edge contributes the arc factor → variable, an Absorbing edge the arc variable → factor, and a Bidirectional edge contributes both — so a single bidirectional edge is already a 2-cycle and makes this false.

That is the correct behaviour, not an artefact: a bidirectional edge is exactly what "implicit" means, and isdag(g) is precisely the predicate "this graph could have been written in Lux".

source
Mycelium.istree — Method
istree(g) -> Bool

Whether the undirected bipartite graph is a tree: connected and loop-free.

This is the property that decides whether message passing is exact. On a tree, two sweeps (inward then outward) give the exact marginals and the exact free energy. Off a tree you are running loopy BP and everything is an approximation — see Loopy Message Passing.md.

Do not confuse with isdag, which is about edge directions and decides whether the graph is Lux-compatible.

source
Mycelium.learnable_factors — Method
learnable_factors(g) -> Vector{Int}

Factor node ids that contribute trainable parameters, per LenticulumCore.islearnable. A graph of non-learnable factors is an inference graph, not a training graph.

source
Mycelium.leaves — Method
leaves(g) -> Vector{Tuple{Symbol,Int}}

Nodes of undirected degree 1 — where a tree sweep starts.

source
Mycelium.parameter_key — Method
parameter_key(node::FactorNode) -> Symbol

The entry of the graph's parameter tree ps (and state tree st) this node reads. Nodes with the same key are tied: they share one parameter vector, and the graph gradient of that entry is the sum of their contributions (plate!, graph.md).

source
Mycelium.parameter_keys — Method
parameter_keys(g) -> Tuple{Vararg{Symbol}}

The distinct parameter_keys of the factor nodes, in order of first appearance: the top-level keys of LuxCore.initialparameters(rng, g). Without ties these are the factor names.

source
Mycelium.tied_factors — Method
tied_factors(g, key::Symbol) -> Vector{Int}

The ids of the factor nodes that read parameter entry key.

source
Mycelium.topological_order — Method
topological_order(g) -> Vector{Tuple{Symbol,Int}}

Nodes in topological order as (:variable, id) / (:factor, id) pairs. Errors unless isdag.

This is the order in which an ordinary forward pass runs, and it exists only for the Lux-compatible case. Cyclic graphs get a FloodingSchedule or a ResidualSchedule instead.

source
Mycelium.variable! — Function
variable!(b::GraphBuilder, name::Symbol, space = nothing) -> Int

Add a variable node; returns its id.

source
Mycelium.variable_degree — Method
variable_degree(g, vid) -> Int
factor_degree(g, fid) -> Int

The number of edges incident to a variable or a factor. For a variable this is the $d_v$ of the Bethe counting number $1 - d_v$; see free_energy.jl.

Polarity resolution

Mycelium.PolarityError — Type
PolarityError(factor, channel, reason)

Raised when a requested message is not legal: the edge direction forbids it, or the factor does not support the resulting polarity.

source
Mycelium.can_emit — Method
can_emit(g, edge_index) -> Bool
can_absorb(g, edge_index) -> Bool

Whether the edge's direction permits a factor → variable (resp. variable → factor) message.

source
Mycelium.check_legal — Method
check_legal(g, fid, polarity)

Verify that a polarity is compatible with the edge directions of this graph, and with the factor's own supports_polarity. Throws a PolarityError naming the offending channel.

The two checks are genuinely different:

  • edge direction is a property of the wiring: an Emitting edge may not be Observed(), an Absorbing edge may not be Unobserved();
  • supports_polarity is a property of the factor: can it be run this way at all?

Together they are the replacement for Lux's acyclicity restriction. A Lux Chain is well-formed iff the wiring is a DAG; a Mycelium graph is well-formed iff every scheduled message passes both checks.

source
Mycelium.legal_sources — Method
legal_sources(g, fid) -> Vector{Symbol}

The channels of factor fid from which it could ever read.

source
Mycelium.legal_targets — Method
legal_targets(g, fid) -> Vector{Symbol}

The channels of factor fid on which it could ever emit, given the edge directions alone. A factor with exactly one legal target is unidirectional in this graph, which is a weaker and more useful notion than LenticulumCore.isunidirectional (a property of the factor).

source
Mycelium.resolve_polarity — Method
resolve_polarity(g, fid, target_channel, available_channels) -> Polarity

Build the Polarity for the message that infers target_channel from the channels in available_channels.

available_channels is the set of channels for which an incoming (variable → factor) message exists and whose edge absorbs. Every other declared channel of the factor becomes Latent().

Precisely one channel is Unobserved(). That is a deliberate restriction for v0: a message addresses one variable. Joint messages over several channels at once are the correct generalisation (and the only way to keep correlations between them — cf. the mean-field laxness of Composition of Bayesian Lenses.md Remark 16), and are noted as future work in polarity_resolution.md.

source
Mycelium.validate — Method
validate(g::FactorGraph)

Structural checks that must hold before any message can be scheduled. Throws on failure, returns g on success.

Checks:

  1. every edge's channel is declared by its factor (LenticulumCore.channels);
  2. every factor has at least one edge (an isolated factor contributes energy nobody reads);
  3. every variable has at least one edge;
  4. no variable is written by two Emitting edges and read by none — a variable that is only ever produced is a dangling output, which is legal but almost always a wiring bug, so it is reported as a warning rather than an error;
  5. a channel and its variable agree in dimension where both declare one, and a DataFactor's vector has its variable's length.
source
Mycelium.validate_parameters — Method
validate_parameters(g, ps) -> nothing

Checks a graph-wide parameter tree before inference or training, which otherwise read a missing key as an empty tree (_subtree) and fail later or not at all:

  • every node whose LuxCore.initialparameters is not empty has its parameter key in ps;
  • that entry has the same names (recursively) and array sizes as the initial parameters (it is not compared by value; a declared output coefficient passed as a parameter is caught here);
  • every frozen path of a node exists in its entry.

Throws an ArgumentError listing every problem. Keys of ps that no node reads are reported in a warning (a misspelt key, say), not an error.

source

Messages and beliefs

Mycelium.Message — Type
Message(belief, iteration)

A belief in transit, tagged with the sweep that produced it. The tag is what lets the scheduler tell a stale message from a fresh one without comparing beliefs.

source
Mycelium.MessageStore — Type
MessageStore(g)

Per-edge storage for both message directions. nothing means "not yet computed", which is distinct from "computed and uninformative" (the latter is TrivialBelief()).

source
Mycelium.belief_distance — Method
belief_distance(a, b) -> Real

A non-negative measure of how much a message changed, used as the convergence criterion in propagate!.

Implemented for the cases that can be answered without densities; otherwise returns Inf, which makes the scheduler run to maxiters rather than silently declaring convergence it cannot verify. Erring towards Inf is deliberate: a false "converged" is much worse than a wasted sweep.

LogPotentialBelief pairs have distance zero only when their wrapped callables are identical (===), and Inf otherwise. This assumes captured mutable data is unchanged; no numerical comparison up to additive constants is attempted. Other potential subtypes retain the conservative Inf fallback.

source
Mycelium.belief_logdensity — Function
belief_logdensity(b::AbstractBelief, x) -> Real

$\log p_b(x)$. Implemented for categorical beliefs ($x$ a state index or label), mixtures (the log of the weighted sum of the components' densities), Gaussians, and callable potentials. Any belief with a density can reweight a SampleBelief in combine. For AbstractPotentialBelief this is a log-potential defined up to an additive constant, not a normalised probability density. Subtypes provide their own evaluation method.

source
Mycelium.can_damp — Method
can_damp(new, old) -> Bool

Whether a convex combination of these two beliefs is defined. false by default, so callers can inspect whether damp will be a no-op.

source
Mycelium.combine — Function
combine(a::AbstractBelief, b::AbstractBelief) -> AbstractBelief

Pool two beliefs about the same variable — the product of densities, in sum-product terms.

This is the hardest operation in the package and is deliberately partial. What is implemented is what can be done honestly for the belief types LenticulumCore currently provides:

caseresultwhy
TrivialBelief with anythingthe other oneit is the unit
two agreeing DiracBeliefsthat Diracidempotent
two disagreeing DiracBeliefsthrowstwo hard clamps in contradiction is a modelling error, not a numerical one
DiracBelief with anythingthe Diraca hard clamp dominates (ρ_in = Inf, per Channels and Polarity.md)
two GaussiansGaussianadd canonical parameters
two categoricals on the same supportcategoricalnormalised pointwise product
SampleBelief with a density or potentialreweighted samplesimportance weighting, no resampling

Everything else throws an informative error. Potential products with categorical beliefs are also refused: converting labels or state indices into points needs an explicit model. See messages.md §"Implementation difficulties".

source
Mycelium.combine_with_overlap — Function
combine_with_overlap(c, d) -> (belief, logZ)

Return the pooled belief and $\log Z = \log \int p_c\,p_d$. For proper beliefs this is the exact log overlap. When d is improper, logZ is defined up to an additive constant depending on d alone, which cancels when normalising mixture weights. For Gaussian pairs, c must be proper when d is; when both are improper (unnormalised exponentials) the product is exact, normalised with its mass in logZ if it is proper and logZ = 0 otherwise. For disjoint categorical support, return (c, -Inf) since the pooled distribution is undefined. Implemented for categorical pairs here and Gaussian pairs in Mycelium's gaussian.jl.

source
Mycelium.damp — Method
damp(new, old, α) -> belief

$\alpha \cdot \text{new} + (1-\alpha)\cdot\text{old}$, the standard remedy for oscillating loopy BP.

Defined only where a convex combination of beliefs makes sense. For DiracBelief with numeric payloads this is interpolation of the values; for anything else, damping is a no-op returning new, inspectable through can_damp. Potentials use this fallback: without a normalisation contract there is no chosen convex-mixture interpretation. Schedules do not automatically report unsupported damping.

Mycelium.excluded_marginal — Method
excluded_marginal(store, g, vid, skip_edge) -> AbstractBelief

The belief at a variable excluding the message that arrived along skip_edge — the variable → factor message of belief propagation.

This exclusion is not an optimisation; it is what makes BP correct. Without it a factor's own previous message is fed back to it as if it were independent evidence, and the belief becomes exponentially over-confident with each sweep. On a tree the exclusion is exactly what makes two sweeps give the true marginals.

Note that we recompute the product over the other edges rather than dividing the full marginal by the skipped message. Division requires densities and is numerically fragile; recomputation costs O(degree) per message and is always defined.

Mycelium.bethe_free_energy — Method
bethe_free_energy(store, g, ps, st) -> (GradedEnergy, st)

The graph free energy, graded into (factors = …, variables = …):

\[\mathbf{F}_{\text{Bethe}} = \bigoplus_f \mathbf{F}^f \ \oplus\ \bigoplus_v (1-d_v)\,(-\mathbf{H}^v)\]

Exact on a tree. On a loopy graph it is the Bethe approximation, whose stationary points are exactly the fixed points of loopy belief propagation (Yedidia–Freeman–Weiss) — so running BP and minimising this quantity are the same activity, which is a genuinely useful thing to know when the two appear to disagree.

With MeanField nodes it is the merged free energy of Riegler et al. (2013), eq. (17): mean-field nodes contribute mean_field_energy and the variable counting numbers count belief-propagation neighbours only. Its stationary points are the fixed points of the hybrid message passing (their Theorem 2). When the belief-propagation part is a forest and the mean-field nodes split it into independent clusters, it is $\mathrm{KL}(q \| p) - \log Z$ for the factorised $q$, an upper bound on $-\log Z$.

Contrast chain_free_energy, which follows AutoBayes Theorem 23 literally and is schedule-dependent.

Uses factor_free_energies, including its cavity edge-direction check.

Mycelium.chain_free_energy — Method
chain_free_energy(Fs) -> GradedEnergy

AutoBayes Theorem 23 applied along a linear order: $\mathbf{F}^{dc} = (\mathbb{E}[\mathbf{F}^c],\ \mathbf{F}^d)$ folded right to left.

Fs is the ordered vector of per-factor vector free energies. Uses LenticulumCore.compose_free_energy, so the nesting matches what Composition of Statistical Games.md describes.

[!warning] This is schedule-dependent and Bethe is not Theorem 23's recursion refers to "downstream", which on a graph is a property of the message order, not of the wiring. Two different schedules give two different decompositions of the same total. Bethe's form has no order in it at all.

They agree when every belief is a DiracBelief (deterministic inference: all expectations are evaluations and all variable entropies vanish), which is exactly the regime the test suite checks. Off it, prefer Bethe for reporting and the chain form for reasoning about a specific message path.

source
Mycelium.counting_number — Method
counting_number(g, vid) -> Int

The counting number $1 - d_v$ of a variable, where $d_v$ counts its edges to BeliefPropagation nodes, and to ExpectationPropagationRule nodes, which count the same way. With every node on belief propagation that is the degree, and this is the Bethe counting number.

A variable of degree 1 counts 0 (nothing to correct: only one factor mentions it). A variable of degree 2 counts -1 (its entropy was counted twice, so subtract one copy). And so on.

Edges to MeanField nodes do not count: a mean-field node contributes an average energy and no entropy, so the variable's own entropy is counted $1 - |N_{BP}(v)|$ times, as in the merged free energy of Riegler et al. (2013), eq. (17). A variable with mean-field neighbours only counts 1: its full entropy, as in naive mean field.

Mycelium.total_counting_number — Method
total_counting_number(g) -> Int

$\sum_f 1 + \sum_v (1 - d_v)$.

This equals the Euler characteristic $|F| + |V| - |E|$, because $\sum_v d_v = |E|$. So it is 1 exactly when the graph is a connected tree, and 1 - L when it has L independent loops.

That single integer measures how badly the Bethe bookkeeping can be wrong: on a tree the counting is exact, and the deficit from 1 is the number of loops the approximation has to pretend are not there.

With MeanField nodes the counting numbers are those of the merged free energy (counting_number), and this sum is no longer the Euler characteristic.

Asserted against euler_characteristic in the test suite, since it is the cheapest possible check that the graph and the free-energy accounting agree.

source
Mycelium.variable_free_energy — Method
variable_free_energy(belief) -> Real

$F_v = -H(b_v)$. A variable has no energy of its own — it is a wire, not a node with a potential — so its free energy is minus its entropy.

The Bethe free energy is $F_\beta = \sum_\alpha c_\alpha F_\alpha$ over factors and variables, with $c_f = 1$ and $c_v = 1 - d_v$. Because $F_v = -H_v$, the variable term is $\sum_v (1-d_v)(-H_v) = +\sum_v (d_v - 1)H_v$: it adds back the entropy that the factor terms subtracted $d_v$ times. (The sign matters only once a belief has non-zero entropy; see free_energy.md §6.)

Mycelium.OptimiserFactor — Type

An optimiser, as a factor attached to an exposed parameter variable.

Cruttwell et al. present optimisers as reparametrisations — boxes sitting above the parameter wire. Mycelium.PriorFactor — Type

A prior over one variable: emits belief, and charges energy nlogp(x) at the variable's current point.

This is AutoBayes Remark 24 exactly: give the prior a trivial inversion, set $l^\pi(x) = -\log p_\pi(x)$ and $H^\pi \equiv 0$, and the composite with a downstream factor has the true variational free energy as its loss. Whether local_free_energy reads incoming variable-to-factor messages. Defaults to false; implement as true for factors that use them, including those forming the Bethe factor belief $b_a \propto f_a \prod_i \mu_{i\to a}$.

Graph free-energy evaluation requires every edge of such a factor to carry variable-to-factor messages (Absorbing() or Bidirectional()). An Emitting() edge raises ArgumentError; use Bidirectional() if the factor also sends messages. A missing message on an edge that can carry one is still passed as nothing to local_free_energy.

Exposed parameters

A parameter block of a factor can become a channel, so that a variable holds the weight, a prior on it is an ordinary factor, and connecting two factors' exposed channels to one variable ties the weight (L-SPEC-003 §1). With the channel observed as a point, any factor works; a belief on it needs the factor's parameter_message and parameter_free_energy.

ExposedFactor

Mycelium.expose — Method
expose(f, names; rng = Random.Xoshiro(0)) -> ExposedFactor

Move the parameter blocks names of f out of its ps and into channels. Each entry of names is a parameter name (the channel gets the same name) or a pair param => channel. A block must be an array; its channel carries vec(block), column-major, of length length(block). Block sizes are read once from initialparameters(rng, f).

  • With every exposed channel observed as a point (DiracBelief), messages and free energies are exactly f's with the blocks substituted (L-SPEC-003 §1.1).
  • An exposed channel may also carry a belief, or be the target of a message, where f implements supports_parameter_polarity, parameter_message and parameter_free_energy (§1.2). Otherwise such a message throws.
  • Connecting exposed channels of several factors to one variable ties the weight (§1.3).

The prior on an exposed weight is a separate factor on its variable, as for any variable. Game-level methods (assemble, energy, free_energy) are not forwarded; the exposed factor is for graphs.

The likelihood message from f to target (one of f's channels or an exposed parameter name) when exposed blocks carry beliefs. msgs holds the incoming beliefs keyed by channel and parameter name; ps lacks the exposed blocks. Everything else

Mycelium.Mycelium — Module
Mycelium

Factor graphs and message passing for Lenticulum.jl.

LenticulumCore says what a factor is (a parameterized statistical game); Mycelium says how factors are wired and in what order they talk. It is the layer that has no counterpart in Lux, because in Lux the wiring is a DAG and the order is implied by it.

The design in five sentences

  1. The graph is bipartite: variables are wires, factors are nodes. Everything with content is a factor — data, priors, losses and optimisers included, following AutoBayes Remark 24. See factors.jl.
  2. Edges are directed, and carry one of Emitting, Absorbing, Bidirectional. A bidirectional edge is exactly what "implicit" means.
  3. A factor → variable message is an inversion $c'_\pi$: the target channel becomes Unobserved(), the channels with incoming messages become Observed(), the rest Latent(), and assemble + invert do the rest. See polarity_resolution.jl.
  4. Scheduling is the whole problem. On a tree, two sweeps are exact; off a tree you are running loopy BP and nothing is guaranteed. See schedules.jl.
  5. The free energy of a graph is the Bethe form: energies add, entropies get a counting correction $(1-d_v)$. That is the same energy/entropy asymmetry AutoBayes identifies, one level up. See free_energy.jl.

Two acyclicity notions, not one

predicateaboutdecides
istree(g)the undirected bipartite graphwhether message passing is exact
isdag(g)the directed multigraphwhether the graph is Lux-compatible

They are independent, and confusing them is the commonest way to be wrong about a factor graph.

Concept notes are in vault/Factor Graphs/; per-file implementation notes sit next to each source file.
