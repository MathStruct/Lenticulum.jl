LP-011 Gradient couplings and isfrozen are declared but unused

Theory (CT-ML wiki): Statistical Game

Original problem (verified before the guards). The design says the choice of gradient coupling is made per edge (connect!(…; coupling = DiagonalCoupling()), ComposedFactor(…; coupling)), and that a frozen factor (isfrozen) differs from a non-learnable one in the backward pass. Neither coupling field had a runtime reader; isfrozen had only its default definition and a top-level conformance assertion checking Bool. No production override returned true and no test/example/tutorial/benchmark selected a non-default coupling. A user setting coupling = ScoreFunctionCoupling() therefore got no error and no gradient effect.

Options.

  1. Implement them as part of the graph-level backward pass (Backward Signatures) and the stop-gradient specification.
  2. Until then, warn (or throw) when a non-default coupling is set, so the setting is not silently ignored.

Option 2 implemented (2026-10-26)

  • connect!, direct/parameterized Edge, and keyword/positional/parameterized ComposedFactor now throw ArgumentError for non-default couplings, explaining that the setting would be silently ignored and naming LP-011 / L-SPEC-002. Fields and types remain.
  • build does not call validate; both now reject every graph factor declaring isfrozen == true, naming the factor. This includes islearnable == false: the existing optimiser-list filter does not implement parameter freezing with preserved input cotangents, and no graph backward path supplies that guarantee.
  • Checks occur at construction/validation only; message passing is unchanged. Accepting DiagonalCoupling() preserves existing behavior rather than inserting AD stops.
  • The two packages’ LP-011 testsets cover all three non-default built-in coupling families (PathwiseCoupling, ScoreFunctionCoupling with and without baseline, ExactCoupling), a custom subtype, constructor bypasses, independent build/validate rejection for both learnability values, errors naming the frozen factor, and default paths.
  • No existing non-default tests or examples needed conversion: the audit found none.

Still open. Option 1, the actual gradient and freezing semantics, remains with L-SPEC-002 Stop Gradient.

Option 1 implementation (2026-10-27)

The maintainer decisions are recorded in L-SPEC-002 Stop Gradient; the option-2 history above is retained. All four built-in coupling annotations are admitted. The parameter driver now reads them, with explicit static-schedule replay for non-diagonal edges and estimates with standard errors for terminal score edges. Unknown annotations still throw. detach is per attachment, freezing is per factor parameter subtree, and straight-through is a separate factor with ForwardDiff and ChainRules rules.

gradient_couplings gives the mixed Jacobian semantics, public keywords, estimator objective and rejected combinations. isfrozen is accepted by build/validate and pins parameters without suppressing upstream derivatives. Optimiser state contains only active coordinates. The LP-008 conformance work present at task start is retained.

The closed-form tests exposed an existing terminology error: fixed cavity messages do not imply fixed posterior beliefs. Today’s diagonal derivative is retained and explicitly labelled fixed-cavity. True posterior EM and exact evidence gradients agree at an exact posterior. A collapsed Gaussian composite also differs semantically from an exposed internal graph wire; its three analytic endpoint coupling choices coincide.

Remaining domains: flooding/residual replay, graph damping in reverse mode, other schedule AD backends, GPU, nonterminal/bidirectional score sampling, stochastic solver inversion estimators, and an implicit graph adjoint. Unsupported combinations raise ArgumentError; this implementation does not claim those capabilities.
